Tamper-proof skill certificate issuer for training institutes

Your certificate is a word-processor file that anyone can edit, and the employer reading it has no way to tell. This tool signs each certificate with your institute's own key and prints a verification code on it. Anyone can check that code offline, in seconds, without contacting you.

Small training institutes, skilling centres and trade schools Ed25519 signed credentials Single binary · no internet

What it does

You set up your institute once: the tool generates a signing key and saves it on your machine with owner-only permissions. From then on, every certificate you issue is signed.

A signed certificate carries a short, printable verification code. The code holds the certificate's details and the signature together, so checking it needs nothing but the code and your published public key — no website to visit, no account, no call to your office. An employer in another city, or in another country, can check it with no internet connection at all.

Change a single character of a signed certificate — one letter of the learner's name, one digit of the hours, the date, the grade, the certificate number — and the code stops verifying. That is the whole point: the details and the signature stand or fall together.

Who it's for

Small training institutes, skilling centres and trade schools that print their own certificates: welding and fitting shops, tailoring and beauty courses, computer and spoken-English centres, driving schools, barangay and panchayat skilling programmes. Anywhere a course ends in a piece of paper that someone later has to trust.

It is equally for the person on the other side. An employer, a college admissions clerk or a recruitment agency can run the same tool in verify mode and get a yes or no, without the institute being involved.

The rule it implements

There is no statute behind this tool. The named rule in the pill above is a cryptographic standard, not a law: Ed25519, the signature scheme defined in RFC 8032, as implemented in the Go standard library's crypto/ed25519.

What the tool signs is fixed and published here, because a signature is only meaningful if everyone agrees on exactly which bytes it covers. The signed field set is these eight fields, in this order:

id
learner_name
course
hours
grade
issued_on
issuer_name
issuer_pubkey

They are encoded one per line as name=length:value after a version header, so the encoding is unambiguous: because each value carries its own byte length, a learner named "AB" who took course "C" can never produce the same bytes as a learner named "A" who took course "BC". Without that length prefix, one signature could cover two different readings of the same certificate.

Fixed parameters, defined once in the code
  • Signature scheme — Ed25519 (RFC 8032). Public key 32 bytes, private key 64 bytes, signature 64 bytes.
  • Encoding version header — omsme-cert/v1. A future field set gets a new header, so an old verifier refuses a new certificate instead of misreading it.
  • Code prefix — CERT1-, followed by unpadded base64url of the signed bytes and the signature.
  • Key file permissions — 0600, owner read and write only.
  • Date format — YYYY-MM-DD, zero padded, rejected if it is not a real calendar date. 2024-02-29 is accepted; 2023-02-29 and 1900-02-29 are not.

These are properties of the signature format, not figures set by any authority, so nothing here expires or needs re-checking against a gazette. Whether a certificate counts for anything — recognition, accreditation, a place on a qualifications framework — is a separate matter decided by your awarding body or regulator. Confirm those requirements with them; this tool neither grants nor affects them.

Install & run

It is one Go file tree with no dependencies: no database, no package manager, no build step beyond go build. Clone the repository, then:

cd verifiable-cert-issuer
go build -o cert-issuer .
./cert-issuer

Open http://127.0.0.1:8080/. To use a different port or file locations:

./cert-issuer \
  -addr 127.0.0.1:9000 \
  -data ./certificates.json \
  -key ./institute-key.json

Verification needs no user interface at all. The same binary checks a code from the command line and exits non-zero if it does not verify, so it drops into a script:

./cert-issuer \
  -verify CERT1-b21zbWUtY2V… \
  -pubkey Uyk5kiJSrdBSye…

The -pubkey value may be the key itself or the path of the public-key file the tool exports. Line breaks and spaces inside a code or a key are ignored, so a code copied off a printed certificate works.

What it stores

Two files on your own machine, and nothing else:

  • The certificate list, a plain JSON file at the -data path. Every certificate you have issued, with its signature and its code. Written through a temporary file and renamed into place, so an interrupted write cannot truncate it.
  • The private signing key, a separate JSON file at the -key path, created with 0600 permissions. The tool warns you if those permissions are ever loosened.

Nothing is sent anywhere. The tool makes no outbound network connections, has no telemetry, loads no fonts or scripts from the internet, and binds to 127.0.0.1 so it is not reachable from the rest of the network. Back up the key file the way you would back up a rubber stamp — and keep it as private.

Features

Set up once

Name your institute, generate a key, and the tool allocates certificate numbers for you from a prefix and the year.

Printable certificate

Each certificate gets a clean printable page with the learner's details and the verification code on it.

Verify screen

Paste a code and a public key: pass or fail, the decoded details, and the list of fields the signature actually covers.

Batch from a spreadsheet

Export a class list as CSV and sign the whole batch. Bad rows are reported by line number; the rest still go through.

Public key export

One short string, in a text file you can email, publish or print, that lets employers verify on their own.

Command-line verify

Checking works with no interface at all and exits non-zero on failure, so it fits into whatever an employer already runs.

How it is used in practice

  1. Generate the institute's key once, back up the key file, and publish the public key on your website and your letterhead.
  2. Issue certificates as learners finish, singly or as a batch from your class spreadsheet.
  3. Print the verification code on the certificate, and send it with the learner's digital copy.
  4. An employer pastes the code and your published public key into the verify screen, or runs the one-line command, and gets pass or fail.

What a pass proves, and what it does not

A pass means two things, and only these two: the certificate was signed by whoever holds the private key matching the public key you supplied, and not one character of the signed details has changed since. It does not mean the institute is accredited, registered or recognised by anyone. It does not mean the course was any good, that the learner attended, or that the grade was earned. Those are questions about the institute, and a signature cannot answer them.
The public key is what decides the answer — never the institute name printed on the certificate. Anyone can generate a key, sign a certificate naming any institute at all, and get a code that is internally consistent. That is why the verify screen refuses to return a pass on the key carried inside a code, and insists on a key you supply from somewhere else. Get the institute's public key from the institute: their website, their letterhead, a file they sent you. Not from the certificate you are checking.
Not yet implemented, and deliberately not pretended: this is not a W3C Verifiable Credential. The codes are this tool's own format and no W3C VC serialisation is produced or accepted. QR codes are not rendered — the verification code is text you print, copy or type. There is also no revocation list and no expiry: once a certificate is issued, its code verifies forever, and nothing in this tool can call it back.
If the private key file is lost, every certificate you have already issued stays verifiable — verification only ever needs the public key, which you have published. What you lose is the ability to issue any more under that key: you generate a new one, publish it too, and from then on employers need the old public key for old certificates and the new one for new ones. If the private key is leaked, anyone holding it can sign certificates in your institute's name that verify exactly like yours, and there is no way to tell them apart or to withdraw codes already in circulation. The only remedy is to generate a new key, publish it, and say plainly from which date the old key is retired. Guard the key file accordingly, and keep a backup somewhere a fire or a dead disk cannot reach.

Open source

MIT licensed, standard library only, no third-party modules. The signing, the encoding and the verification rules live in one small package with table-driven tests covering every rule described above, including each single-field tamper and corrupted codes. Read it, change it, run it entirely offline.
